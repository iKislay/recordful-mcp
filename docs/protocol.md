# Bridge protocol (v2)

The transport between `recordful-mcp` (server) and the Recordful extension's service worker (client). The source of truth is `src/protocol/messages.ts`; the extension keeps a hand-written mirror in `recordful/src/pages/Background/agentBridge/`. Any breaking change bumps `PROTOCOL_VERSION` on both sides. v2 added pairing and moved to a new path, so v1 and v2 peers never talk to each other.

## Transport

- WebSocket at `ws://127.0.0.1:<port>/recordful-agent-bridge/v2` (default port `47823`, the only one the Chrome Web Store build uses).
- JSON text frames only, each at most 1 MiB.
- The server rejects the HTTP upgrade (403) unless `Origin` is `chrome-extension://<id>` with an allowed ID: the Chrome Web Store build (`hkcgjbkibidgbefehehenlmhjanjaopc`) plus any in `RECORDFUL_BRIDGE_ALLOWED_EXTENSION_IDS` (`*` allows any, for development).

## Handshake

```
server → client  {type:"challenge", protocolVersion:2, serverNonce, serverId, app}
client → server  {type:"hello", protocolVersion:2, clientNonce, proof, client:{extensionId, extensionVersion, browser}}
server → client  {type:"welcome", sessionId, proof}
```

- `serverId` is a UUID kept in the machine's pairing file (`~/.recordful/agent-bridge.json`), shared by every recordful-mcp process on the computer. `app` is the MCP client's display name ("Claude Code"), from its MCP `initialize`.
- Nonces are 32 random bytes, hex-encoded.
- `proof = hex(HMAC-SHA256(secret, "recordful-agent-bridge:<role>:<serverNonce>:<clientNonce>"))`, with role `client` for the hello proof and `server` for the welcome proof. `secret` is this extension's pairing secret for this `serverId` (or, for scripted runs against development builds, a shared `RECORDFUL_BRIDGE_TOKEN`).
- The server checks that `client.extensionId` matches the Origin, then checks the proof in constant time against the secrets it holds for that extension.
- The client checks the server proof and **refuses to process any request** until it passes. Secrets are never sent after pairing.
- Handshake deadline: 5 s.

## Pairing

An extension with no secret for this `serverId` asks to pair, but only on a user gesture (toolbar icon, shortcut, or switching AI agents on). Automatic reconnects never prompt.

```
server → client  {type:"challenge", ...}
client → server  {type:"pair_request", protocolVersion:2, client}
server → client  {type:"pair_code", code:"0427"}
   (Recordful opens its pairing window naming the app and showing the code;
    the agent's tool calls return PAIRING_PENDING with the same code)
client → server  {type:"pair_accept", secret}   then the usual hello, signed with it
             or  {type:"pair_reject"}            server closes 4403
```

- `secret` is 32 random bytes, base64url (43 characters), generated by the extension. Both sides store it: the server in its pairing file, keyed by extension ID, and the extension in `chrome.storage.local.agentBridgePairings`, keyed by `serverId`.
- The user has 2 minutes to answer (then close 4411). A newer pair_request replaces an open one. A denial is reported to the agent as `PAIRING_DENIED` for 2 minutes.
- If the server rejects a stored secret (its pairings were reset), the extension forgets it and, if a gesture started the connection, asks to pair again straight away.

## Steady state

| Direction | Message |
| --- | --- |
| server → client | `{type:"request", id, method, params}` |
| client → server | `{type:"response", id, ok:true, result}` or `{type:"response", id, ok:false, error:{code, message, data?}}` |
| client → server | `{type:"event", name, data?}` (reserved for state push) |
| client → server | `{type:"ping", ts}` every 20 s; the server answers `{type:"pong", ts}` |

The 20 s ping also keeps the MV3 service worker alive (Chrome 116+ extends worker lifetime while a WebSocket is active). The server drops a session that has been silent for 65 s.

One authenticated session at a time: a newer authenticated connection supersedes the old one (close `4409`).

## Close codes

| Code | Meaning |
| --- | --- |
| 4400 | Malformed or unexpected message |
| 4401 | Authentication failed (deliberately not more specific) |
| 4403 | The user declined pairing |
| 4408 | Handshake timeout |
| 4409 | Superseded by a newer session |
| 4410 | Heartbeat timeout |
| 4411 | Pairing not answered in time, or replaced by a newer request |
| 4426 | Protocol version mismatch (the client backs off to its longest retry delay) |

| `recording.start` | `tabId?` (default: the armed tab), `timeoutMs?` (1000–120000, default 30000) | `{outcome:"recording", tabId, recordingType, waitedMs, recordingStartTime}` or `{outcome:"pending", hint, ...}`. | `recording.stop` | `timeoutMs?` | `{outcome:"stopped", recording:{kind:"cloud", videoId, viewUrl, editUrl} \| {kind:"local", takeId}, plan, editorTabId?, editorUrl?, hint?}`. Waits up to 20 s for a local recording to be written out |
| `recording.pause` / `recording.resume` | — | `{outcome:"paused"/"recording", changed}` |

| `page.navigate` | `url` (http/https), `timeoutMs?` (1000–60000, default 20000) | `{url, title, loaded, waitedMs, hint?}` |

| `page.scroll` | `ref`, or `direction` (`up`/`down`/`left`/`right`) with `amount?` px | `{scrolledTo, box}` or `{scrolled, position, container, atEnd}` |
| `page.waitFor` | `text` or `ref`, `state?` (`visible`/`hidden`), `timeoutMs?` (100–60000, default 10000) | `{satisfied:true, waitedMs}` or error `WAIT_TIMEOUT` |
| `page.screenshot` | — | `{mimeType:"image/jpeg", data (base64), width, height, scale, tabId, url, title}` |
| `account.get` | — | `{cloud, signedIn, pro, plan, email, site, features}` |
| `takes.list` | — | `{takes:[{takeId, bytes, recordedAt, uploadedVideoId, isLastRecording}]}` |
| `video.upload` | `takeId?`, `title?`, `visibility?` (`private`/`workspace`/`public`), `force?` | `{videoId, takeId, title, viewUrl, editUrl, stage:"uploading", totalBytes, camera:"included"\|"skipped"\|"none"}`, or `{alreadyUploaded:true, ...}`. Answers once the video exists; the upload continues in the extension |
| `video.get` | `videoId?` | `{videoId, title, visibility, durationSeconds, createdAt, viewUrl, editUrl, stage:"uploading"\|"processing"\|"ready"\|"failed", uploadedBytes, totalBytes, error?}` |
| `video.list` | `limit?` (1–50, default 10), `query?` | `{videos:[{videoId, title, createdAt, durationSeconds, visibility, viewUrl, editUrl}]}` |
| `video.transcript` | `videoId?`, `start?` (default true) | `{videoId, status:"done", text, vtt, viewUrl, editUrl}` or `{status:"working"\|"uploading"\|"none"}` or `{status:"failed", reason}`. One look; the MCP server and CLI poll it to wait |

Requests run on queues in the extension: recorder methods (`recording.*`, `capture.probe`) one at a time on one queue, page methods one at a time on another, uploads on a third, and the read-only methods on none, so they never wait behind the others.

### Video methods

- **As the signed-in user.** The extension calls recordful.app's API (`RECORDFUL_API_BASE_URL`) with its own session token, refreshing it once on a 401. Agents never hold a credential.
- **Plans.** Uploads and transcripts need Recordful Pro. `video.upload` and `video.transcript` check the account first and fail with `PRO_REQUIRED` (data `{plan:"free", upgradeUrl}`) or `NOT_SIGNED_IN` (data `{plan:"signed-out", signInUrl, upgradeUrl}`); the message says recording still works.
- **Upload.** The same steps as the web editor's "Share": `POST /videos/create`, then per file `POST /uploads`, signed part URLs from `/uploads/:id/parts` (5 MiB parts, each retried twice), `PUT` to storage, `POST /uploads/:id/complete`, then `PATCH /videos/:id` for title and visibility. A camera recorded as its own file is included only when it starts within 0.25 s of the screen, since only an edit can line it up otherwise. Progress lives in `chrome.storage.session.agentUploads`; an upload cut off by a worker restart reports `UPLOAD_INTERRUPTED`. Uploaded takes are remembered in `chrome.storage.local.agentUploadedTakes`, so a take isn't uploaded twice.
- **Last recording.** Stopping or uploading sets `chrome.storage.session.agentLastRecording`; video methods without a `videoId` use it, else the newest video in the account.
- **Transcript.** `GET /videos/:id/transcript?text=1` returns `text` and `vtt` once done; `POST` starts one (Pro, rate-limited per workspace).

## Peers

A second recordful-mcp process (another AI app, or the CLI) connects to the owner at `ws://127.0.0.1:<port>/recordful-agent-bridge/v2/peer` and forwards calls through the owner's connection to the extension. Requests to this endpoint must not carry an `Origin` header (browsers always send one, so web pages can't reach it); at most 16 peers.

```
owner → peer   {type:"peer_challenge", protocolVersion:2, serverNonce}
peer  → owner  {type:"peer_hello", protocolVersion:2, clientNonce, proof, app?}
owner → peer   {type:"peer_welcome", proof}
peer  → owner  {type:"peer_call", id, op:"state"|"wait"|"request", app?, timeoutMs?, method?, params?}
owner → peer   {type:"peer_result", id, ok:true, result} | {type:"peer_result", id, ok:false, error:{code, message, data?}}
```

Proofs are `HMAC-SHA256(peerSecret, "recordful-agent-bridge:peer:<serverNonce>:<clientNonce>")` and `...:peer-server:...`, with `peerSecret` from the shared pairing file, so only processes of the same user (reading the same file) can join. Peers ping every 20 s. When the owner exits, peers race (with jitter) to take the port over; the extension reconnects to the new owner. The CLI only ever joins: if nothing owns the port it starts a detached helper (`recordful-mcp daemon`) that owns it and exits after 30 idle minutes.

### Page methods

- **Target tab.** The tab being recorded (`recordingUiTabId`) while a recording runs, otherwise the *armed* tab: the one where the user last clicked the Recordful icon or pressed a Recordful shortcut (`chrome.storage.session.agentBridgeArmedTab`). Never any other tab, whichever is in front. No armed tab → `NOT_ARMED`. `status.get` reports it as `agent.armedTab`.
- **Refs.** `page.snapshot` gives each element a ref (`e1`, `e2`, …) that stays the same for that element while it is on the page. Refs belong to one document: after a navigation or reload, any ref → `STALE_REF` until the agent takes a new snapshot.
- **Execution.** The worker sends `{type:"recordful-agent-page", action, params, cursor, expectDocId}` to the content script (`chrome.tabs.sendMessage`), which acts with synthetic DOM events and answers `{ok, result | error, docId, cursor}`. It draws its own cursor (a fixed, closed-shadow overlay, `pointer-events:none`), glides it to each target, shows a ripple on click and types with jittered per-key delays. Recordful's own UI is excluded from snapshots and hit tests.
- **Limits of synthetic input.** Pages see `isTrusted:false` events. Links, buttons, checkboxes, labels and form submits work; native `<select>` popups, file pickers and anything that requires a real user gesture (pop-ups, clipboard, fullscreen) do not. `page.type` on a `<select>` chooses the matching option instead. `page.press` performs the key's default effect itself (Enter submits or activates, Tab moves focus, Backspace deletes, Space toggles, PageDown scrolls). Iframes are not covered.
- `page.click` and `page.press` report a navigation they started (`navigation:{url, title, loaded | sameDocument}`), and wait up to 10 s for it to load. `page.waitFor` polls from the worker, so it survives navigations.
- `page.screenshot` needs the target tab to be the active tab of a visible window (`TAB_NOT_ACTIVE` otherwise). It is downscaled to at most 1280 px wide and re-encoded until it fits under the 1 MiB frame cap.

## Error codes

`NOT_CONNECTED`, `DISCONNECTED`, `TIMEOUT`, `BRIDGE_UNAVAILABLE`, `INVALID_PARAMS`, `PAIRING_PENDING` (with `data.code`), `PAIRING_DENIED`, `TRANSCRIPTION_FAILED` (bridge side); for video methods `NO_RECORDING`, `NOT_SIGNED_IN`, `PRO_REQUIRED`, `VIDEO_NOT_FOUND`, `NOT_UPLOADED`, `STORAGE_FULL`, `RATE_LIMITED`, `TRANSCRIPTION_UNAVAILABLE`, `UPLOAD_FAILED`, `UPLOAD_INTERRUPTED`, `CLOUD_UNAVAILABLE`, `CLOUD_UNREACHABLE`, `CLOUD_ERROR` (extension side); `UNKNOWN_METHOD`, `ALREADY_RECORDING`, `NOT_RECORDING`, `NO_TARGET_TAB`, `TAB_NOT_RECORDABLE`, `START_FAILED`, `STOP_FAILED`, `INTERNAL`, and for page methods `NOT_ARMED`, `TAB_NOT_ACTIVE`, `PAGE_NOT_SCRIPTABLE`, `STALE_REF`, `ELEMENT_NOT_INTERACTABLE`, `ELEMENT_OBSCURED` (with `data.obscuredBy`), `NAVIGATION_FAILED`, `WAIT_TIMEOUT` (extension side). Codes are a public contract: new codes can be added, but existing ones are never repurposed.

## Extension adapter

`recordful/src/pages/Background/agentBridge/`:

| File | Role |
| --- | --- |
| `index.js` | Starts the client, registers the icon/shortcut listeners and the `open-agent-settings` message |
| `client.js` | Connection, handshake, pairing, ping, request dispatch, the toolbar badge. Inert while AI agents is off. Connects on a toolbar-icon click, a shortcut or switching AI agents on (one attempt each), after a dropped session (6 retries with jitter, 1 s → 30 s, about 80 s total), and on worker boot if a session was live (`chrome.storage.session.agentBridgeWanted`). It never polls, because Chrome logs every refused WebSocket on `chrome://extensions` |
| `storageKeys.js` | The storage the client and the AI agents page share: the switch, pairings, status, the open pairing request and the user's decision |
| `auth.js` | WebCrypto HMAC, nonces and secrets, mirroring `src/auth/handshake.ts` |
| `commands.js` | Recorder methods. Each sends the same message as the matching keyboard shortcut (`start-stream`, `stop-recording-tab`, `pause-recording`) |
| `pageCommands.js` | Page methods: picks the target tab, navigation, waits, screenshots, and relays the rest to the content script |
| `armedTab.js` | Remembers the tab the user handed over (icon click or shortcut) |
| `errors.js` | Error codes |
| `../../Content/agentPage/` | Content-script side: snapshot and refs, the rendered cursor, click/type/press/scroll |
| `../../Agents/` | `agents.html`: the AI agents page (switch, status, setup command, paired apps) and, with `?pair=1`, the pairing window |

The adapter ships in every build, including the Chrome Web Store one, and does nothing until the user turns AI agents on (Recordful popup → More → AI agents). Development builds may bake in a shared secret (`RECORDFUL_AGENT_BRIDGE_TOKEN`) and a port (`RECORDFUL_AGENT_BRIDGE_PORT`) for scripted test runs; DefinePlugin compiles both to empty strings in any other build, and with a baked secret the switch and pairing window are skipped.
